## 一、核心理念与架构契约

### 1.1 定位：“查看、理解与定位”
Agent Workbench 是一个专为复杂多仓架构和 AI/大模型工作流设计的**只读研发工作台**：
* **数据事实单一来源**：所有的 Feature、任务分解、验证记录均保存在工作流仓 `agent-workbench` 的 `.workspace` 和 Markdown 规范文件中；
* **非侵入式消费**：插件通过子进程协议 `kit.py inspect` 以纯只读方式获取数据，**绝不擅自修改任何业务代码或工作流文件**；
* **宿主原生 Git 代理**：所有 Git 的写操作（分支切换、Commit、Push、Merge、冲突解决）均无缝转交 IntelliJ IDEA 原生能力，不自行实现脆弱的 Git 命令包装。

## 二、工作区与多仓工程配置规范

### 2.1 推荐目录组织（父工程模式）
在大中型项目中，一个业务特性通常涉及多个微服务仓和前端仓。强烈建议在磁盘上创建一个父目录：

```text
my-app-workspace/                         # 推荐用 IDEA 打开此根目录
├── agent-workbench/                      # 工作流管理仓
│   ├── .workspace/
│   │   └── workspace.json                # 业务仓与工作区登记表
│   └── docs/development/features/        # 需求规范与文档
│       └── order-export-optimization/
│           ├── requirements/
│           │   └── requirements.md       # PRD 需求规范
│           └── tasks.md                  # 任务分解
├── order-service/                        # 后端订单微服务（独立 Git 仓）
├── payment-service/                      # 后端支付微服务（独立 Git 仓）
└── admin-frontend/                       # 前端管理后台（独立 Git 仓）
```

### 2.2 `workspace.json` 登记配置示例
在 `agent-workbench/.workspace/workspace.json` 中登记需要纳入工作台管理的业务代码仓：

```json
{
  "version": 1,
  "workspace": {
    "name": "E-Commerce App Workspace",
    "repositories": [
      {
        "id": "order-service",
        "path": "../order-service",
        "defaultBaseBranch": "develop"
      },
      {
        "id": "payment-service",
        "path": "../payment-service",
        "defaultBaseBranch": "develop"
      },
      {
        "id": "admin-frontend",
        "path": "../admin-frontend",
        "defaultBaseBranch": "main"
      }
    ]
  }
}
```

### 2.3 IDEA 多 Git 根目录映射（`.idea/vcs.xml`）
用 IDEA 打开父目录后，请确保各子仓均已登记为 Git 根目录：
1. 打开 `Settings | Version Control | Directory Mappings`；
2. 确认 `order-service`、`payment-service` 等目录的 VCS 均已设置为 `Git`；
3. *注：若有新接入的仓库未被映射，在插件界面的仓库列表中点击单仓操作时，插件会自动弹出提示询问“接入并继续”，确认后将自动添加映射。*

## 三、工作台四大核心视图详解

### 3.1 左侧导航工具窗口（ToolWindow）
位于 IDE 左侧边栏的 **Agent Workbench** 面板：
* **顶部状态区**：展示工作区名称与连接状态（`● 运行正常`）；
* **4 宫格快捷导航**：
  * `总览`：一键打开中央工作区综合面板；
  * `记录`：查看历史流水线与任务 Run 记录；
  * `体检`：即时查看环境 Doctor 诊断结果；
  * `配置`：调整 Kit 绑定路径与 Python 环境。
* **智能分支匹配横幅**：
  * 当你本地的某个业务仓正切在某个 Feature 的工作分支时，面板顶部会自动浮现：  
    `💡 当前检出分支属于需求: order-export-optimization`，点击即可一秒直达该需求。
* **需求卡片列表**：
  * 卡片直观展示需求 Slug（加粗）、中文标题、状态胶囊徽章（`testing` / `development`）；
  * 若当前本地正好切在该需求分支，会高亮显示 `[📍 当前检出]` 专属蓝色胶囊。

### 3.2 需求总览与说明（首页首屏三合一）
进入具体需求后，默认展示第一标签页 **「总览与说明」**：
* **完全无滚动设计**：左侧 58% 与右侧 42% 采用响应式分栏，**所有核心模块首屏同框可见**；
* **左侧：PRD 规范快速阅读**：
  * 自动检索并渲染需求的 `requirements.md`（或 `requirements/requirements.md`）；
  * 具备高保真 Markdown 排版，文章篇幅较长时在容器内平滑垂直滚动，不挤占其他面板；
* **右上：任务拆解与执行**：
  * 紧凑展示该需求下所有子任务的完成勾选框、任务编号（如 `[T01]`）与进度条；
* **右下：关联代码仓卡片**：
  * 逐行清晰展示当前需求涉及的微服务仓名称；
  * 分支流向明确标注（例如：`develop ➔ feat/order-export`）；
  * 实时状态指示（`● 干净` 或 `3 个未提交变更`）。

### 3.2.1 Feature 代码评审

在 `Settings | Tools | Agent Workbench` 的“代码托管服务”添加 GitHub 或 GitLab 服务，再为每个服务保存只读 Token。Token 由 IDEA/Rebased 的密码库管理，`agent-workbench.xml` 不保存 Token。GitHub 建议使用只覆盖目标仓并授予 `Pull requests: Read` 的细粒度 Token；GitLab 使用具备 `read_api` 的 Token。

打开 Feature 的“变更”后，默认显示“代码评审”子页，只查询该 Feature 已登记的仓库与工作分支。它不依赖当前检出分支，因此网页手动创建、已合并或已关闭的同仓 PR/MR 都可以显示。一个分支有多个候选评审时，插件要求选择，不自动猜测；没有评审、Token 权限不足和网络失败会显示为不同状态。需要使用 SSH 主机别名时，可在对应服务中配置，例如 `github-personal`。“需求分支已提交”和“当前工作目录”仍可从相邻子页按需查看。

### 3.3 代码变更与比对（跨仓差异视窗）
在顶部子标签栏切换至 **「代码变更与比对」**：
* **关联仓库切换**：支持下拉选择需求绑定的不同微服务仓，支持**持久记忆选中项**，后台刷新绝不跳回；
* **一键抓取基线 (Fetch)**：点击 `[🔄 抓取远程 (Fetch)]` 即可异步同步远程代码并自动重新计算提交差异；
* **双分支比对入口**：点击 `[⇥ 打开已提交 Diff]`，直接呼出 IntelliJ 原生双分支比对全屏对话框；
* **变更文件清单**：双击任意文件，无需切分支即可查看该文件的纯净代码修改。

### 3.4 辅助工具栏
* **折叠侧栏**：右上角提供 `[折叠侧栏]` 按钮，方便在 13/14 寸小屏笔记本上一键全屏阅读长篇规范；
* **查看文档 (F4)**：快速在 IDEA 主编辑器中打开底层 Markdown 原文；
* **在工程中定位**：点击即可让 Project View 资源管理器直接定位并展开该需求的目录。

---

### 3.5 接手包与历史检索

- Feature 详情的“复制接手提示词”会在 Kit 支持时先打开接手包预览，显示当前任务、阶段、最近验证、来源和估算 token；可复制全文或从来源列表跳转原文。旧 Kit 自动使用原有 brief。
- 左侧“历史检索”按关键词搜索当前工作区的需求、设计、计划和验证记录，并可按仓库、生命周期筛选。双击结果打开原文，右键可复制带位置的片段。
- 两项能力都只读取现有记录，不修改 Feature、Git 或验证状态。

## 四、Git 变更比对与心智模型

### 4.1 非检出比对原理（Non-checkout Diff）
传统开发中，想要对比功能分支和基线分支的代码，必须先暂存本地文件并 `git checkout` 切换分支。  
**Agent Workbench 彻底打破了这一限制：**
1. 插件利用 Git 底层对象数据库（Git Object Blob），直接提取基线 commit 与需求 commit 进行对比；
2. **无论你本地当前检出的是什么分支**（哪怕是 `test`、`bugfix` 或者包含未提交代码），双击打开的文件对比**永远是纯净的「基线版本 ➔ 需求分支」**。

### 4.2 为什么比对树节点后会显示当前分支名（如 `test`）？
当你点击 `[打开已提交 Diff]` 呼出比对对话框时，左侧树状结构的仓库根节点后可能会附带一个灰色的分支名（例如 `test`）。  
* **原因**：这是 IntelliJ IDEA 原生 VCS 树状组件的固定环境变量标签，其作用是提醒开发者“你本地硬盘当前物理停留在哪个分支”；
* **请放心**：它**绝不是**比对的目标！请观察比对标签页的最顶层标题，标明的一定是：  
  `Changes Between develop and feat/order-export`，证明实际参与比对的正是你的基线与需求分支。

### 4.3 基线分支的远程优先机制
团队协作中，公共基线分支（如 `develop` 或 `main`）会频繁合入其他同事的代码：
1. **优先匹配远程**：插件在解析基线分支时，优先读取本地已经 fetch 过的 `origin/<baseBranch>`；
2. **随时一键更新**：点击 `[🔄 抓取远程 (Fetch)]` 按钮，后台拉取远程最新 commit 索引后，比对界面会自动以最新的远程基准重算差异；
3. **安全无冲突保证**：`git fetch` 是只读抓取，不触碰任何本地工作区物理文件，绝对不会引起代码冲突。

## 五、日常协作工作流推荐

推荐的日常敏捷协同模式：

```text
1. 启动 IDEA 打开父目录
   └── 插件自动连接工作区，在左侧 Feature 列表选择今日开发任务
2. 阅读需求规范
   └── 在「总览与说明」中同时对照左侧 PRD 与右上任务拆解
3. 编码与本地提交
   └── 在各业务子仓中开发代码，完成本地 commit
4. 审查自身改动
   └── 在「代码变更与比对」中先点击 [🔄 抓取远程 (Fetch)] 确保基线最新
   └── 双击文件清单或点击 [打开已提交 Diff] 完成 Self-Code-Review
5. 验证与归档
   └── 在「验证与测试」中记录执行结果与验收 checklist
```

## 六、常见问题与排障指南 (FAQ)

### Q1: 关联代码仓卡片显示“Git 现场未就绪”是什么原因？
* **原因 A**：你本地该业务仓中尚未创建或拉取需求记录中的工作分支（例如记录需要 `feat/order-export`，但你本地只有 `master`）；
* **原因 B**：分支命名存在细微差异（例如大小写不一致或多敲了下划线）；
* **处理方法**：在对应仓库中创建或切换到匹配的分支即可，插件将在 500ms 内自动识别并变更为就绪状态。

### Q2: 需求概述（PRD）内容区域显示空白？
* **排查路径**：检查工作流仓中对应 Feature 的规范文件存放路径。
* **文件命名规范**：插件会按顺序自动检索：
  1. `docs/development/features/<slug>/requirements/requirements.md`
  2. `docs/development/features/<slug>/requirements.md`
  3. `docs/development/features/<slug>/README.md`
  若文件名拼写不符，重命名为上述标准命名即可自动加载。

### Q3: 切换关联仓库下拉菜单时，会不会又跳回第一个？
* **解答**：不会。插件已内置智能状态追踪与防重置保护。当后台触发定时轮询或 Git 状态更新时，插件会始终锁定并保持你当前选中的微服务仓。

### Q4: 如何在没有网络的环境下使用代码比对？
* **解答**：插件具备智能双向回退机制。在离线无法连接远程 origin 时，插件会自动使用本地现存的 `refs/heads/<baseBranch>` 开展对比，离线开发体验同样平滑。
